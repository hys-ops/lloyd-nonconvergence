Small matrices and shared checks

Remove repeated checks rather than special-case small inputs

The newest change reduced the first-step penalty on 8×8 and reversed it on 32×128 in a synthetic follow-up. The same cleanup shortened the archived application suite by 2.21%.

What slowed down

When a good warm start already passed the first check, there was no iteration to save. The validation cost was then visible: in a synthetic 1,000-call stream with nearly every solve finishing on its first update, stock versus the first warm-start candidate took 29.5 versus 41.6 ms on 8×8, and 44.7 versus 50.7 ms on 32×128.

What changed mathematically

We reused the minimum of each marginal to test both positivity and the eligibility threshold, avoided an unnecessary temporary array for the log-seed bound, and evaluated the L2 residual directly on the real vector. This is an implementation cleanup, not a new mathematical error criterion. It did not change the requested tolerance, where the solver checks, or which inputs are eligible. It also does not route every small matrix back to stock, which would lose gains when the initial guess needs more updates.

Matched follow-up and broader results

In the separate 1,000-call follow-up, 32×128 took 42.16 ms with the revised check code versus 46.58 ms with stock. The remaining 8×8 gap narrowed from 12.75 to 1.05 microseconds per call within that follow-up. This is a controlled synthetic regression, not a measured production bottleneck.
